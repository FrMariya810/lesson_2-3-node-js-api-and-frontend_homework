# Карта проекта

Это справка по готовой инфраструктуре. Требования и баллы находятся в [условии](../assignment.md). Алгоритмы выдачи, возврата и обновления интерфейса нужно разработать самостоятельно.

## Данные и сервер

В shared/loan.ts объявлены Loan, LoanInput и Snapshot. Тело HTTP имеет тип unknown: даже существующий тип LoanInput не проверяет присланный JSON.

server/routes.ts связывает адреса с функциями server/loans.ts и оборачивает результат в { data: ... }. Ошибки доходят до общего обработчика server/index.ts. HttpError принимает HTTP-статус, строковый код и сообщение. Чтение тела готово в server/http.ts.

server/seed.ts задаёт исходные записи и общий фонд STOCK. Рабочие данные — data/loans.json. Не храните второй изменяемый «остаток» в файле: он определяется журналом.

## Контракт хранилища

В практике использовались готовые add/confirm. Здесь один новый интерфейс — store.edit: правило операции описываете вы, чтение и запись выполняет хранилище.

store.list() возвращает Promise с актуальным массивом выдач.

store.edit(change) получает функцию, а не готовый массив. У неё две разные задачи:

- Изменить переданный массив draft: именно он будет сохранён. Простое возвращение другого массива не меняет draft.
- Вернуть результат для вызывающего кода — например, одну запись. Это значение не заменяет массив в файле.

Promise edit завершается после записи. Если функция выбросила ошибку, файл не меняется; если draft не изменён, новая запись в файл не выполняется.

Отвлечённый пример (реальный store.edit работает с Loan[]): функция получила массив [1, 2], добавила в него 3 и вернула строку «готово». Сохранённое значение — [1, 2, 3], результат вызова — «готово». Если она только вернула [1, 2, 3], исходный массив остался [1, 2].

Весь вызов edit выполняется последовательно с другими операциями. Правило, зависящее от текущих выдач, проверяется на актуальном массиве внутри этой операции. Не вызывайте store.list или ещё один edit внутри change: они ожидают освобождения той же очереди.

Чтение JSON, проверка его структуры, временный файл, замена рабочего файла и очередь готовы. Не подавляйте ошибку записи и не отвечайте успехом до завершения Promise.

## Клиентская часть

src/api.ts содержит готовый `request<T>`: возвращает data успешного ответа, а при HTTP-ошибке или отсутствии связи выбрасывает Error. getSnapshot работает. issue и takeBack — явные заглушки.

src/main.ts хранит snapshot и busy. show, setBusy и render отвечают за сообщение, блокировку и отображение. Загрузка сохраняет последний список при отказе. submitIssue и submitReturn не реализованы; счётчики не вычисляются.

src/ledger.ts создаёт строки и передаёт id выбранной записи в переданную функцию. Он не выполняет HTTP и не меняет входные данные. Переписывать его в веб-компонент не требуется.

## Команды

| Команда | Назначение |
| --- | --- |
| npm run dev:api | API на 3001; после изменений server/shared перезапустите |
| npm run dev | Vite на 5173; запросы /api перенаправляются серверу |
| npm run build | Проверка типов клиентской и серверной частей, затем сборка клиентской части |
| npm run preview | Собранная клиентская часть на 4173, API нужен отдельно |
| npm run data:reset -- --yes | При остановленном API: вернуть Алину и Бориса и удалить маркер сбоя |
| npm run demo:fail-next | При следующей реальной записи вызвать отказ до изменения файла |
| npm run demo:clear | Удалить неиспользованный маркер |

GET и повтор уже выполненного возврата не записывают файл и не расходуют маркер. Для опыта отказа выбирайте активную выдачу.

При повреждении файла сервер сообщает об ошибке и не стирает данные автоматически. Для учебного восстановления есть явный сброс. Все имена исходного набора вымышлены.
